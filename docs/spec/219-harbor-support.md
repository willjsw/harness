# Harbor 레지스트리 지원

Harbor 를 레지스트리 지원 목록에 올린다. 근거는 사람이 Harbor 를 상대로 돌린 실측 결과다(2절).
실측이 통과 기준을 모두 채우면 지원 목록에 한 줄을 더하고(3절), 하네스가 레지스트리에 기대는 것과
실측으로 확인된 Harbor 사실을 운영 안내로 적는다(4절). 하네스 코드·설정·자동 테스트는 바뀌지 않는다.

명령(`harness registry check --push` · `harness registry login` · `harness preset push` · `harness pull`),
레지스트리 클라이언트의 동작, 지원 목록의 형식과 위치는 #218 이 정한다. 이 명세는 그 위에 Harbor 한 줄과
운영 안내를 얹는다.

정본 위치:

| 대상 | 정본 |
|---|---|
| 지원 목록 | #218 이 정한 문서와 형식 |
| 레지스트리 운영 안내 | `src/templates/managed/docs/workflow/registry.md` — 관리 파일. render 가 이 리포와 대상 리포의 `docs/workflow/` 에 사본을 깐다 |
| 운영 안내 목차 | `src/templates/managed/docs/workflow/README.md` 의 문서 표 |
| 사람용 지원 범위 | `README.md` 의 "지원 범위" 절 |
| 실측 입력 | 이슈 #219 의 댓글 (2-4) |

## 1. 바뀌는 것과 바뀌지 않는 것

- 바뀌는 것은 문서뿐이다 — 지원 목록 한 줄(3절), 운영 안내 새 파일과 목차 한 행(4절), README "지원 범위" 의
  안내 문장 하나(4-5)
- 하네스 코드(CLI · 레지스트리 클라이언트), 설정 키, 생성 파일, 회귀 테스트는 바뀌지 않는다. Harbor 를 이름으로
  가르는 코드를 두지 않는다
- Harbor 를 이 리포의 자동 테스트와 CI 에 넣지 않는다. 실제 레지스트리에 붙는 확인은 사람이 손으로 돌린다
  (`.ai/project/testing.md` "하지 않는 것")
- 결정 기록을 새로 쓰지 않는다
- 이슈는 3·4절의 변경을 담은 리뷰 요청이 머지될 때 끝난다

## 2. 실측 입력

### 2-1. 착수 전제

실측은 사람이 한다. 조직 Harbor 의 자격증명과 내부 호스트가 필요하고, 에이전트는 그것을 다루지 않는다.

아래 넷이 모두 성립해야 구현을 시작한다.

1. #218 이 통합 브랜치에 머지되어 있다 — 위 명령과 지원 목록 형식이 있다
2. #217 이 통합 브랜치에 머지되어 있다 — 4-2 의 "대상 리포 CI" 가 가리키는 CI 게이트와 그 검사가 있다
3. 실측 입력 댓글(2-4)이 이슈 #219 에 있고, 통과 기준(2-3)을 모두 채운다
4. 조직 보안 담당이 Harbor 버전 문자열을 공개 리포에 적는 것을 허용했다 — 댓글의 "버전 공개" 칸이 그 확인이다

구현자는 첫 변경 전에 이슈 댓글에서 실측 입력을 찾는다. 댓글이 없거나, 칸이 비었거나, 실패한 항목이 있으면
아무것도 바꾸지 않고 멈춰 보고한다 (5절).

### 2-2. 실측 항목

준비물:

| 준비물 | 조건 |
|---|---|
| 확인용 프로젝트 | 태그 불변 규칙과 서명 강제를 걸지 않은 Harbor 프로젝트 |
| 운영 프로젝트 | 태그 불변 규칙과 서명 강제가 걸린 Harbor 프로젝트 |
| robot 계정 | 운영 프로젝트에 push 자격. preset 리포 CI 의 시크릿으로 둔다 |
| 개발자 계정 | 확인용 프로젝트에 push 자격, 운영 프로젝트에 pull 자격만 |
| 대상 리포 | 버려도 되는 하네스 설치 리포 하나 |

통과 기준에 드는 항목:

| 번호 | 항목 | 누가 · 어디서 | 통과 |
|---|---|---|---|
| M1 | 왕복 확인 — `harness registry check --push` | 개발자 계정, 확인용 프로젝트. 실행마다 새 태그로 올린다 | #218 이 정한 검사 항목이 전부 통과한다 |
| M2 | CI push — preset 리포 CI 가 `harness preset push` 를 돌린다 | robot 계정, 운영 프로젝트. credential helper 없이 다른 도구(`docker login` 등)가 써 둔 `config.json` 의 `auths` 로 인증한다. `harness registry login` 은 쓰지 않는다 | push 가 성공한다 |
| M3 | 정책 아래 pull — M2 에서 올리고 서명을 붙인 아티팩트를 `harness pull` 로 받는다 | 개발자 계정, 운영 프로젝트, 버려도 되는 대상 리포 | pull 이 성공해 vendoring 과 lock 이 쓰인다 |

- M2 의 서명은 preset 리포 CI 가 하네스 밖의 도구로 붙인다. 하네스는 서명하지 않는다
- 세 항목은 같은 Harbor 인스턴스에서 같은 버전으로 돈다

기록만 하는 항목(통과 기준에 들지 않는다):

| 번호 | 항목 | 어떻게 |
|---|---|---|
| O1 | referrers 조회 경로 — referrers API(`api`)와 tag schema fallback(`fallback`) 중 어느 쪽이 쓰였나 | M1 에서 `harness registry check` 의 `referrers` 항목이 보고한다 |
| O2 | 서명 강제가 preset 아티팩트에 적용되나 | 운영 프로젝트에서 서명을 붙이기 전의 아티팩트를 pull 해 본다 |
| O3 | Harbor UI 가 preset 의 사용자 정의 `artifactType` 을 어떻게 표시하나 | UI 에서 본다 |

O1 은 M1 이 돌면 언제나 기록된다. O2 · O3 은 관측하지 않았으면 "관측 안 함" 으로 적는다.

### 2-3. 통과 기준

- M1 · M2 · M3 이 모두 통과했다
- 인증과 O1 이 기록되어 있다
- 지원 목록에 올리는 버전은 이 실측이 돈 Harbor 버전 하나다

### 2-4. 댓글 형식

사람이 이슈 #219 에 아래 형식으로 남긴다. 다시 실측하면 새 댓글을 남기고, 구현자는 가장 최근의 실측 입력
댓글을 쓴다.

```markdown
## 실측 입력 — Harbor

| 칸 | 값 |
|---|---|
| Harbor 버전 | <Harbor 가 보고하는 버전 문자열> |
| 버전 공개 | 허용 확인 |
| 실측일 | <YYYY-MM-DD> |
| 검증 수단 | 수동 실측 |
| M1 왕복 확인 | 통과 / 실패: <실패한 검사 항목 이름> |
| 인증 | none / basic / bearer |
| M2 CI push (config.json auths) | 통과 / 실패 |
| M3 정책 아래 pull | 통과 / 실패 |
| O1 referrers 경로 | api / fallback |
| O2 서명 강제 적용 | 서명 전 pull 거부 / 서명 전 pull 허용 / 관측 안 함 |
| O3 UI 의 artifactType 표시 | <관측 내용> / 관측 안 함 |
```

- "버전 공개" · "검증 수단" 은 고정 값이다. 버전 공개는 2-1 의 4 를 확인했다는 표시이고, 검증 수단은 사람이
  M1 · M2 · M3 을 손으로 돌렸다는 표시다
- "인증" 은 M1 의 check 출력에서 `auth` 항목이 거친 방식(`none` · `basic` · `bearer`)만 옮긴다. 범위(`pull,push`)는
  옮기지 않는다
- "O1 referrers 경로" 는 M1 의 check 출력에서 `referrers` 항목의 값(`api` · `fallback`)을 옮긴다

### 2-5. 공개 기록에서 빼는 것

리포가 공개다. 실측 입력 댓글, 지원 목록, 운영 안내, 커밋 메시지, 리뷰 요청 본문 어디에도 아래를 적지 않는다.

- Harbor 의 호스트 이름 · 주소, 프로젝트 · 저장소 이름, 전체 참조
- robot 계정 · 개발자 계정의 이름, 자격증명 · 토큰
- 실측한 인스턴스의 정책 설정 — 불변 규칙의 패턴, 서명 도구와 그 설정, 보존 정책
- 내부 URL — CI 실행 기록 링크를 포함한다
- 명령 출력 원문 — 호스트와 참조가 들어 있다. 항목별 결과만 옮긴다

지원 목록과 운영 안내에는 실측한 인스턴스가 조직이 운영하는 것이라는 사실도 적지 않는다. 적는 것은 Harbor 와
버전, 항목별 결과뿐이다.

## 3. 지원 목록 한 줄

#218 이 정한 지원 목록에 Harbor 한 줄을 더한다. 형식은 #218 의 것을 그대로 쓰고, 칸마다 실측 입력(2-4)에서 채운다.

| 지원 목록 칸 | 값 |
|---|---|
| 레지스트리 | `Harbor` |
| 검증한 버전 | 실측 입력의 "Harbor 버전" 칸 그대로 |
| referrers | 실측 입력의 "O1 referrers 경로" 칸 — `api` 나 `fallback` |
| 인증 | 실측 입력의 "인증" 칸 — `none` · `basic` · `bearer` 가운데 하나 |
| 검증 수단 | 실측 입력의 "검증 수단" 칸 — "수동 실측" |

- 버전을 범위로 넓히지 않는다 — "2.x" · "이상" 같은 표기를 쓰지 않는다. 다른 버전은 따로 실측해 줄을 더한다
- 실측 입력에 없는 값은 적지 않는다
- 2-5 를 지킨다

## 4. 운영 안내

### 4-1. 위치

- 새 관리 문서 `src/templates/managed/docs/workflow/registry.md`, 제목은 "레지스트리 운영"
- `src/templates/managed/docs/workflow/README.md` 의 문서 표에 한 행 — 문서 `registry.md`, 답하는 것은
  "preset 을 레지스트리로 배포할 때 무엇을 준비하나. 누가 올리고 누가 받나"
- 정본을 고친 뒤 `harness render` 로 이 리포의 `docs/workflow/` 사본을 갱신한다

문서는 4-2 · 4-3 · 4-4 를 이 순서로 담는다. 4-2 · 4-3 은 벤더 중립으로 쓰고, 벤더 이름은 4-4 에만 나온다.

### 4-2. 하네스가 레지스트리에 기대는 것

| 주제 | 적을 내용 |
|---|---|
| 저장소 | push 할 저장소(이름 공간)는 미리 있어야 한다. 하네스는 저장소 · 권한 · 불변 규칙 · 보존 · 복제를 만들거나 바꾸지 않는다 — 플랫폼 팀이나 IaC 의 일이다 |
| 자격 | push 자격과 pull 자격을 나눈다. 운영 저장소의 push 는 preset 리포 CI 의 전용 계정만 하고, 개발자는 pull 만 한다 |
| 인증 | 하네스는 자격증명을 저장하지 않는다. 개발자는 credential helper 를 두고 `harness registry login` 으로 로그인한다. 헬퍼가 없는 CI 는 다른 도구(`docker login` 등)가 써 둔 `config.json` 으로 인증하고, `harness registry login` 을 쓰지 않는다 |
| 고정 | 하네스는 lock 의 digest 로 고정한다. 태그가 다시 쓰여도 이미 고정한 프로젝트는 바뀌지 않는다. 태그 불변 규칙은 권장이다 — 같은 태그가 다른 내용을 가리키는 혼선을 막는다 |
| 서명 | 서명은 preset 리포 CI 가 붙이고, 강제는 레지스트리 정책이 한다. 하네스는 서명하지도 검증하지도 않는다. 레지스트리가 서명 강제를 이미지가 아닌 아티팩트에도 적용하는지는 레지스트리마다 확인한다 |
| 대상 리포 CI | 레지스트리에 붙지 않는다. 커밋된 vendoring 과 lock 을 검사한다 |

vendoring · lock 의 위치와 CI 검사의 이름은 #216 · #217 이 정한 것을 쓴다.

### 4-3. 레지스트리 확인

- `harness registry check --push` 는 태그 불변 규칙과 서명 강제를 걸지 않은 확인용 저장소에서 돌린다.
  실행마다 새 태그로 올린다
- 올린 확인용 아티팩트는 남는다. 하네스는 지우지 않는다 — 레지스트리의 보존 정책으로 정리한다
- 태그 불변 규칙과 서명 강제 아래의 흐름은 check 가 아니라 실제 `harness preset push`(서명 포함)와
  `harness pull` 로 확인한다
- 지원 목록으로 가는 링크를 단다

### 4-4. Harbor

- 검증한 버전은 이 문서에 다시 적지 않고 지원 목록을 가리킨다
- 실측 입력의 M2 · M3 결과를 적는다 — credential helper 가 없는 CI 가 `config.json` 으로 인증해 push 했고,
  태그 불변 규칙과 서명 강제가 걸린 프로젝트에서 서명된 아티팩트를 pull 했다
- O1(referrers 조회 경로)을 적는다
- O2 · O3 은 관측된 것만 적는다. "관측 안 함" 인 칸은 적지 않는다
- Harbor 의 프로젝트 · robot 계정 · 태그 불변 규칙 · 서명 정책을 만드는 절차는 적지 않고 Harbor 공식 문서로 넘긴다
- 2-5 를 지킨다

### 4-5. README "지원 범위"

- "지원 범위" 절에 레지스트리 운영 안내로 가는 링크 한 문장을 더한다
- Harbor 의 실측 사실은 README 에 다시 적지 않는다 — 운영 안내 한 곳에 둔다

## 5. 멈추는 조건

| 조건 | 동작 |
|---|---|
| 착수 전제(2-1)가 하나라도 성립하지 않는다 | 착수하지 않는다. 구현자는 아무것도 바꾸지 않고 빠진 전제를 보고한다 |
| 실측 항목 M1 · M2 · M3 가운데 하나라도 실패했다 | Harbor 를 지원 목록에 올리지 않는다. 이 이슈는 착수하지 않는다 |
| 실패 원인이 준비물(자격 · 프로젝트 설정 · CI 시크릿)에 있다 | 사람이 준비물을 고쳐 다시 실측하고 새 실측 입력 댓글을 남긴다 |
| 실패 원인이 하네스의 레지스트리 클라이언트에 있다 | 사람이 클라이언트 수정 이슈를 만든다. 수정은 OCI 표준 범위 안에서 하고, 벤더 이름으로 가르지 않으며, Distribution 회귀를 함께 확인한다. 그 이슈가 머지된 뒤 실측을 다시 돌려 새 실측 입력 댓글을 남긴다 |
| 구현 중 실측 입력에 없는 Harbor 사실이 문서에 필요해진다 | 지어내지 않는다. 멈추고 필요한 관측 항목을 보고한다 |

이 이슈 안에서는 코드를 고치지 않는다.

## 6. 보호 문서 개정 범위

없음. 이 이슈는 구성 요소 · 용어 · 신뢰 경계 · 테스트 층 · 담당 범위를 더하지 않는다. 레지스트리 클라이언트와
그에 따른 용어 · 신뢰 경계 · 테스트 층은 #218 이 반영한다.

## 7. 한계

- 지원 목록의 Harbor 줄은 실측한 버전 하나에 대한 것이다. 다른 버전에서 같은지는 다시 실측해야 안다
- 실측은 인스턴스 하나에서 돈다. 인증 방식 · 프록시 · 정책 설정이 다른 인스턴스에서는 결과가 다를 수 있다
