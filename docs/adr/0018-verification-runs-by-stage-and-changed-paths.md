# 18. Verification runs by stage and changed paths

Date: 2026-10-08

## Status

Proposed

## Context

검증 일괄(`script/run-lint-test.sh`)은 매 커밋 앞에서 전부 돌고, post-commit 훅이 같은 트리를 한 번 더 전부 돌렸다.
이 리포에서 한 번은 약 4분(회귀 테스트가 그 87%)이었다. 이슈 넷의 `/work` 구간을 실행 지표로 재면 벽시계 시간의
52~98% 가 검증이었다 — 이슈 #60 은 215분 중 160분, 검증 25회. 같은 트리를 두 번 검증한 연속 실행이 337회 중 120회였다.

검증이 막는 위험이 생기는 시점은 셋이다 — 커밋(되돌리기 어려운 것: 시크릿 · 형식 · 생성물), 리뷰어에게 넘길 때(push),
통합 브랜치에 들어갈 때(머지). 비싼 단계(회귀 테스트)는 뒤의 둘에서만 녹색이면 리뷰 회차를 깨진 코드로 쓰지 않는다.
한편 이 리포는 merge commit 으로 머지해 중간 커밋이 이력에 남고, `git bisect` 는 커밋마다 녹색이라는 보장을 쓴다.

검토한 대안.

- post-commit 훅만 끈다. 커밋당 한 번은 줄지만 커밋마다 전부 도는 비용(수 분)이 그대로다
- 커밋 전 검증을 없애고 CI 에만 맡긴다. 리뷰어가 깨진 리비전을 받아 회차를 쓴다. CI 결과는 원격이라 루프가 기다리지 않는다
- 변경 경로만 보고 단계를 고른다(통과 기록 없이). 통합 브랜치 기준 diff 는 브랜치 전체를 매번 다시 보므로 커밋마다 같은
  단계가 돈다. 직전 커밋 기준이면 커밋 사이에 실패한 채 넘어간 변경을 놓친다

## Decision

우리는 검증을 **단계별 시점과 통과 기록**으로 돌리기로 한다.

- 단계마다 시점을 둔다(`on` = `commit` · `push`). 커밋 전에는 `run-lint-test.sh --commit` 이 commit 단계만,
  push 전에는 pre-push 훅이 전부를 돈다(`verify.pre_push`). CI 는 언제나 전수다
- 단계마다 마지막으로 통과한 작업 트리의 해시를 git 공통 디렉터리에 남기고(`verify.incremental`), 그 뒤 바뀐 파일이
  단계의 경로(`paths`)에 하나도 걸리지 않으면 건너뛴다. 기준이 "마지막 통과" 라서 실패한 채 넘어간 변경도 다음에 다시 본다
- post-commit 재검증은 기본으로 끈다(`verify.post_commit`). 사람이 검증 없이 한 커밋은 pre-push 와 CI 가 받는다
- 하네스 스크립트 회귀 테스트는 `script/` 가 바뀔 때만 도는 단계로 옮긴다(`verify.script_tests`)

이 리포는 회귀 테스트를 `test_on = "push"` 로 둔다. 커밋 전에는 컴파일 · UI 단위 테스트 · 스크립트 회귀만 돈다.

## Consequences

- 커밋 전 검증은 바뀐 경로의 단계만 돈다. 같은 트리를 다시 검증하면 즉시 끝난다
- 이 리포에서 커밋 사이 중간 커밋은 회귀 테스트를 거치지 않는다. bisect 는 `--first-parent` 로 머지 단위를 먼저 좁힌다
- 통과 기록은 트리 내용만 본다. 도구 버전 · 환경 변수가 바뀌었으면 `--no-cache`(또는 `HARNESS_VERIFY_CACHE=off`)로 돈다
- 경로를 좁게 적으면 그 밖의 의존 변경을 놓친다. 경로를 비운 단계는 무엇이든 바뀌면 돈다 — 모르면 비운다
- pre-push 는 커밋이 아니라 작업 트리를 검증한다. push 는 보통 깨끗한 트리에서 하므로 같다
- 대상 리포의 기본값은 지금처럼 테스트를 커밋 전에 돈다(`test_on = "commit"`). 바뀌는 것은 post-commit 이 꺼지고 push 전
  검증이 생기는 것, 그리고 통과 기록으로 같은 트리를 다시 돌지 않는 것이다
