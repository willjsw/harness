# 21. Workflows are block graphs run by the harness

Date: 2026-10-18

## Status

Proposed

## Context

절차는 `harness.toml` 의 단계 목록에서 render 한 문서이고(0007), 오케스트레이터 LLM 이 그 문서를 읽고 수행한다. 단계 종류는
넷(agent · script · prompt · gate)이고 직선으로만 잇는다. `work` 의 분기와 루프 — 리뷰 결과에 따른 수정 · 재리뷰, 회차 상한,
사람에게 넘기기 — 는 조각 산문(`src/templates/workflows/work/branch.md` · `limits.md`)에만 있다. 단계 누락이나 순서 바뀜을 막을
수단이 없고, 세션이 끊기면 열린 리뷰 요청 때문에 착수 판정이 거부해 이어 돌 수 없다. 사람이 설정과 UI 에서 분기 · 루프가 있는
절차를 조립하려면 그 흐름을 문서가 아니라 데이터로 가져야 한다. 명세는 `docs/spec/208-workflow-block-engine.md`.

제약.

- 에이전트 CLI 와 모델은 사람마다 고른다. 러너는 개인 레이어의 값이고 실행 시점에 정해진다
- 하네스는 표준 라이브러리만 쓴다(`.ai/AI_AGENT.md` 4장). JSON Schema 라이브러리를 쓸 수 없다
- 에이전트 CLI 의 출력은 들어오는 입력이다(`.ai/project/architecture.md` "신뢰 경계"). script 단계의 명령이 에이전트 명령 가드
  없이 돌 수 있는 근거는 그 명령이 커밋된 설정에서 온다는 것뿐이다
- 리뷰 회차는 리뷰 명령 하나가 센다(0004). 리뷰 판정은 리뷰어가 낸 구조화 데이터를 하네스가 검증한다(0014)
- 이미 중괄호 문법이 넷 있다 — render 치환 `{{VAR}}` · `{{INCLUDE:<경로>}}`, 조각의 단계 참조 `{{step:<id>}}`, 설정 값 자리표시
  `{clone}` · `{project}`, 벤더 argv 템플릿(`expand()`)의 `{role}` · `{model}`
- 이 결정은 절차 하나를 고치는 것이 아니다. 제어 흐름의 책임을 LLM 에서 하네스 모듈로 옮기고, 프로젝트 설정과 preset 이 쓰는
  외부 형식을 정한다(`.ai/adr.md` "언제 쓰는가" 의 계층 경계 · 데이터 포맷)

검토한 대안.

- 제어 흐름 — 지금처럼 오케스트레이터가 문서를 따른다. 단계 누락 · 순서 바뀜 · 세션 단절의 문제가 그대로다
- 제어 흐름 — agent 절차에서도 배선과 출력 참조를 받아 문서로 그리고 LLM 이 따르게 한다. 강제할 수 없으므로 고치려는 문제가
  남는다. 넓게 받았다가 나중에 좁히면 그 키를 쓴 프로젝트 · preset 이 깨진다
- 제어 흐름 — workflow 블록까지 새 키 전부를 driver 전용으로 둔다. agent 절차는 지금과 같지만, agent 로 남는 절차에는 확장 지점이
  없어 preset 이 그 절차를 통째로만 교체할 수 있다
- 제어 흐름 — 설정에 조건식 언어를 둔다. 설정이 로직을 갖고, render 검증과 UI 편집의 대상이 식이 된다
- 진입점 — driver 절차에도 슬래시 커맨드를 둔다. 세션의 Bash 도구는 실행 시간이 제한되고, 게이트에서 터미널 입력을 받을 수
  없으며, 바깥 세션의 맥락을 소모한다
- 템플릿 문법 — 같은 이름 공간을 쓰되 `run` 을 셸 문자열로 두고 값을 `shlex.quote` 로 인용해 넣는다. 셸 기능은 남지만 자리표시가
  따옴표 안에 놓이는 경우처럼 문맥에 따라 인용이 깨지는 것을 render 가 보장하기 어렵다
- 템플릿 문법 — `run` 에 치환 문법을 두지 않고 값은 환경 변수로만 넘긴다. 주입 경로는 없지만 `{mr}` 같은 짧은 배선이
  `"$HARNESS_VAR_MR"` 가 되어 셸이 다시 필요해지고, agent · prompt 입력에 쓸 문법이 따로 필요하다
- 구조화 출력 — 벤더 CLI 의 출력 스키마 옵션을 필수로 하고 그 인자를 선언한 벤더만 분기하는 agent 단계의 러너가 되게 한다.
  옵션의 유무와 형태가 벤더마다 다르고(2026-10-18 이 기기에서 claude 2.1.302 의 `--json-schema <스키마 문자열>`, codex 0.155.1 의
  `--output-schema <파일>`), 러너가 개인 값이라 같은 절차가 사람에 따라 돌기도 하고 거부되기도 한다. 0014 가 같은 근거로 기각했다
- 구조화 출력 — 벤더 옵션을 쓰지 않는다. 계약은 성립하지만 형식 위반을 줄이는 보조를 버린다
- 기록 — 0007 을 대체한다. 0007 의 Decision(단계는 설정, 문서는 render, 조각은 id 로 참조)은 이 결정 뒤에도 그대로이고 바뀌는
  것은 Consequences 의 단계 종류 서술이다. 결정이 바뀐 것이 아니므로 `.ai/adr.md` 의 대체 규칙에 맞지 않는다(0014 · 0017 선례)

## Decision

우리는 절차를 블록(script · agent · prompt · gate · workflow)과 outcome → 다음 단계 배선(`next`)의 그래프로 정의하고, 절차마다
실행 방식(`execute`)을 골라 driver 절차는 하네스의 드라이버가 그 그래프를 결정론으로 실행하게 한다.

- 설정은 배선만 한다. 판단은 블록 안에 두고 조건식 언어를 두지 않는다. 블록 하나는 outcome 하나와 출력(JSON 객체, 없을 수 있다)을
  내고, 배선이 outcome 을 같은 절차의 단계나 끝 상태 `done` · `stop` · `handoff` 로 잇는다. `next` 가 없는 절차는 암묵 배선으로
  지금 의미(성공하면 다음 단계, 실패하면 멈춤, 마지막 단계가 성공하면 끝)를 유지한다. 실행 방식의 기본값은 agent 다
- 데이터는 이름 공간을 고정한 자리표시로만 흐른다 — `{issue}`, 절차 변수 `{<변수>}`(`set` 이 단계 출력의 최상위 키에서 올린 값),
  `{steps.<id>.out.<키>}`. 필터 · 기본값 · 식 · 중첩 경로가 없다. script 블록의 `run` 은 셸을 거치지 않고 인자로 나눈 뒤 원소마다
  자리표시를 풀며, 푼 값은 원소 하나로 남는다 — 벤더 argv 템플릿(`expand()`)과 같은 규칙이다. render 가 참조를 정적으로 검증하고,
  하위 절차는 바깥 절차의 변수를 읽기만 한다
- agent 블록의 구조화 출력은 하네스의 검증이 계약이다. 역할 계약의 지시와 프롬프트의 스키마로 형식을 요구하고, 드라이버가 표준
  라이브러리로 JSON Schema 부분 집합을 검증한다. 어기면 outcome 은 `failed` 다. 벤더의 출력 스키마 옵션은 그 CLI 로 인자를
  확인해 벤더 선언에 적은 벤더에서만 붙이는 보조다
- driver 절차의 진입점은 `harness run <절차> <이슈>` 하나이고 슬래시 커맨드를 만들지 않는다

강제할 수 없는 문서 수행이 아니라 하네스가 실행해야 단계 누락과 순서 바뀜을 막고 끊긴 실행을 이을 수 있고, 셸을 거치지 않는
자리표시라야 에이전트 출력이 셸 해석에 닿지 않으며, 벤더 옵션에 기대지 않아야 러너 선택이 절차의 성립을 바꾸지 않는다.

## Consequences

- 0007 을 대체하지 않는다. 0007 Consequences 의 "단계 종류는 넷(agent·script·prompt·gate)이고 UI 는 그 종류만 그린다" 부분을 이
  결정이 대체한다 — 블록은 다섯이고 배선이 있다. 0007 의 Decision 은 그대로다
- 0014 를 대체하지 않는다. 0014 는 리뷰 판정에 한정된 결정이고, 이 결정은 같은 원칙(벤더 옵션에 기대지 않고 하네스 검증이 계약)을
  agent 블록 전반으로 넓힌다
- 0004 는 그대로다. 회차는 리뷰 명령 하나가 센다. driver 에서도 전용 스크립트를 가진 역할(`code-reviewer`)은 agent 블록으로 부를 수
  없고 script 블록이 리뷰 명령을 부른다. 드라이버의 단계 · 방문 상한(`max_steps` · `max_visits`)은 보조 안전장치다
- agent 절차는 직선 단계와 workflow 블록만 받는다. 배선 · 스키마 · 절차 변수 · 출력 참조는 driver 전용이고 agent 절차에 있으면
  render 가 거부한다. 단계가 없는 절차는 하위 절차로만 둘 수 있고(확장 지점) 불리면 곧바로 `done` 이다. 부르는 절차와 하위 절차의
  실행 방식이 같아야 한다
- 자리표시 문법이 프로젝트 `harness.toml` 과 preset 으로 퍼진다. 배포한 뒤 문법을 바꾸면 소비 리포의 절차 정의를 모두 고쳐야 한다
- script 블록에는 셸 기능(파이프 · 리다이렉트 · `$` 확장)이 없다. 필요하면 스크립트 파일로 뺀다. script 블록에는 에이전트 명령
  가드가 걸리지 않는다 — 명령은 커밋된 설정에서 오고 git 훅은 그대로 걸린다
- 스키마는 설정 밖 파일이다 — 하네스 동봉(`src/harness/schemas/`)과 프로젝트 소유(`.ai/project/schemas/`) 두 자리. 문법은 표준
  라이브러리로 검증할 수 있는 부분 집합이고, 표에 없는 키워드는 render 가 거부한다. 스키마를 쓰는 역할 계약은 출력 절에 그 이름과
  필드 뜻을 적는다
- 벤더 옵션 없이 도는 러너는 형식 위반이 더 잦을 수 있다. 위반은 `failed` 로 배선을 따라간다
- 끝나지 않은 driver 실행은 0016 의 클론 키 아래에 실행 상태를 남기고, 같은 클론에서만 `--resume` 으로 잇는다. 재개는 진행 중이던
  단계를 처음부터 다시 돈다 — 그 단계가 남긴 부수 효과(커밋 · 댓글 · 회차 라벨)는 되돌리지 않는다
- driver 의 쓰기 역할은 헤드리스 실행 하나에 벤더 선언의 권한 인자(`driver_write`)를 받는다. 헤드리스 실행에 `--bare` 를 쓰지
  않는다 — 설정에 정의된 훅(명령 가드)을 건너뛰기 때문이다
- 블록 · 배선 · 실행 방식 · 드라이버 · 실행 상태는 `.ai/project/` 의 담당 범위 · 아키텍처 · 용어 · 테스트 문서에 반영한다
