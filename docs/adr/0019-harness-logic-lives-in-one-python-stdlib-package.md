# 19. Harness logic lives in one Python stdlib package

Date: 2026-10-10

## Status

Proposed

## Context

하네스 CLI 는 `src/bin/harness` 한 파일(#96 이 들어간 시점에 5천 줄 남짓)과 옆의 지표 모듈 `src/bin/harness_metrics.py` 다.
대상 리포에 깔리는 관리 스크립트(`script/`)는 셸과 파이썬으로 따로 로직을 갖는다. 스택은 python3 3.11 이상 · 표준 라이브러리만
· 의존성 0 이다(`.ai/AI_AGENT.md` 4장).

조직 공용화 로드맵의 Requirement 들 — 설정 계층(#207), 블록 엔진(#208), 관리 스크립트 · 가드 · 훅 · 리뷰 루프의 이식(#209 ~ #213),
preset · 레지스트리(#216 ~ #219) — 이 이 CLI 위에 코드를 더한다. 한 파일이면 병렬 브랜치가 같은 파일을 고쳐 충돌하고, 새 코드를
어디에 둘지 정하는 규칙이 없다. 로직이 셸과 파이썬에 나뉘어 있으면 같은 값(표지, 설정 해석)을 두 언어가 따로 읽고, 테스트도
언어마다 따로 둔다.

묶는 조건이 넷이다.

- 대상 리포의 고정 사본은 커밋되는 소스 사본이고 그 리포의 정본이다(0005). 하네스는 사본의 변경을 막지 않고 감지한다(0015)
- 소스 리포는 사본 없이 자기 `src/bin/harness` 로 돈다(0013)
- 실행 경로 셋(`src/bin/harness` · `.harness/bin/harness` · Homebrew 의 `bin/harness`)을 git 훅 · 검증 일괄 · CI · 권한 규칙 · UI 가 부른다
- pre-push 와 리뷰 루프는 미추적 파일이 없는 작업 트리를 요구한다. 리포 안에 `__pycache__` 가 생기면 막힌다. 그래서 지표 모듈과
  클론 키 모듈은 바이트코드 쓰기를 끄고 불러오고, 진입 스크립트는 바이트코드 캐시를 받지 못해 실행마다 다시 컴파일된다

명세는 `docs/spec/206-split-cli-into-package.md` 다.

검토한 대안.

- 한 파일을 유지하고 필요할 때 옆에 모듈을 더한다(지표 모듈의 방식). 모듈을 어디에 두고 서로 어떻게 부를지 규칙이 없다. 옆 모듈이
  하나 늘 때마다 install 의 복사 목록, 고정 사본 대조의 짝, 회귀 테스트가 복제하는 파일 목록이 함께 늘어난다
- 하나의 아카이브(zipapp)로 묶어 배포한다. 0015 가 기각한 이유 그대로다 — 풀어서 고칠 수 있어 변경 감지에 얻는 것이 없고,
  빌드 단계와 Homebrew 포뮬러 변경이 더해진다
- 네이티브 컴파일(Nuitka · Cython · mypyc). 실행 시간의 대부분이 외부 프로세스 · 네트워크 · 에이전트 대기라 얻는 것이 작다.
  플랫폼마다 빌드가 필요하고 표준 라이브러리 밖의 도구에 기대게 되어 소스 설치 · 의존성 0 정책과 맞지 않는다
- 관리 스크립트의 로직을 셸에 남긴다. 값과 판정을 셸과 파이썬이 따로 갖는 상태가 이어지고, 셸 쪽 로직은 프로세스 안에서 함수
  단위로 시험할 수 없다

## Decision

우리는 하네스 로직을 Python 표준 라이브러리만 쓰는 패키지 `harness` 하나에 둔다.

- 패키지는 소스 리포의 `src/harness/`, 고정 사본의 `.harness/lib/harness/`, Homebrew 설치의 `libexec/harness/` 에 있다
- 진입 스크립트 `bin/harness` 는 파이썬 버전 확인, 바이트코드 위치, 패키지 경로만 정하고 `harness.cli.main()` 을 부른다. 실행 경로
  셋은 그대로다
- 빌드나 네이티브 컴파일 없이 소스 그대로 python3(3.11 이상)로 돈다. 새 외부 의존을 두지 않는다
- 바이트코드는 리포 밖, 기기 단위 상태 아래에 쌓고 리포에는 남기지 않는다
- 관리 스크립트의 로직도 이식하면서 이 패키지로 옮긴다. 셸은 git 훅이 CLI 를 부르는 shim 과, 이식하는 동안 기존 경로를 지키는
  호환 shim 으로만 남는다

옆에 모듈을 더하는 방식을 택하지 않는 것은 모듈이 늘 때마다 설치 · 대조 · 테스트의 목록이 함께 늘기 때문이다. 아카이브와 네이티브
컴파일을 택하지 않는 것은 감지와 속도에서 얻는 것이 없는데 빌드 단계와 의존이 생기기 때문이다.

## Consequences

- 0005 · 0013 · 0015 를 대체하지 않는다. 사본은 여전히 그 리포의 정본이고 전역 CLI 는 여전히 넘긴다. 소스 리포는 여전히 사본 없이
  `src/bin/harness` 로 돈다. 변경은 여전히 막지 않고 감지한다. 달라지는 것은 사본 구성에 `.harness/lib/` 가 더해지고, 해시 기록과
  전역 CLI 대조의 짝에 패키지 파일이 들어간다는 것이다
- 모든 설치본의 고정 사본 구성과 `.harness/managed` 의 사본 줄이 다음 install 에서 바뀐다
- Homebrew 포뮬러가 패키지 디렉터리를 `libexec` 에 넣어야 한다. 포뮬러는 이 리포 밖이라 사람이 탭 리포에서 고친다. 패키지가 든
  `main` 이 배포되기 전에 옛 트리와 새 트리 모두에서 설치되도록 바꾼다. 늦으면 그 사이 업그레이드한 기기의 전역 CLI 와 그것을 부르는
  UI 가 멈춘다. 고정 사본으로 도는 훅 · 검증 일괄 · CI 는 영향을 받지 않는다
- 바이트코드 캐시가 기기 단위 상태(등록부 아래 `.cache/pycache/`)에 생긴다. 하네스는 정리하지 않고, 지워도 다음 실행이 다시 만든다.
  그 아래 바이트코드는 CLI 가 실행하는 코드다
- 대상 리포의 `.gitignore` 가 `lib/` 처럼 이름만 적은 규칙을 가지면 고정 사본 일부가 커밋되지 않는다. 하네스는 이것을 보지 않는다
- 새 명령은 명령 모듈 하나와 명령 표 한 줄이고, 여러 명령이 쓰는 코드는 공용 모듈에 둔다. 모듈 경계와 의존 방향은
  `.ai/project/architecture.md` 가 갖고, 이 리포의 `[verify]` 가 의존 방향을 검사한다. 뒤의 Requirement 들은 이 패키지의 모듈로 들어온다
- 패키지 모듈을 프로세스 안에서 불러 함수 단위로 시험할 자리가 생긴다(`src/test/unit/`, 소스 리포에서만 돈다). 셸 회귀 테스트는 외부
  계약(인자 · 표준 출력 · 종료 코드)을 본다
- 3.11 미만 Python 에 대한 안내는 진입 스크립트가 그 Python 도 해석하는 문법으로 쓰여 있다는 데 기댄다
