# 20. Config is resolved in layers

Date: 2026-10-18

## Status

Proposed

Supersedes [1. One config generates the harness](0001-one-config-generates-the-harness.md)

## Context

하네스의 규칙 값은 대상 리포의 `harness.toml` 하나에 있고(0001), 설치는 기본 설정 전체를 그 파일로 복사한다. 그래서 모든 프로젝트가
기본값 전체의 사본을 갖고, 하네스가 기본값을 바꿔도 이미 깐 사본은 따라오지 않는다. 조직과 스택이 같은 값을 여러 리포에 나눠 주려면
(preset 받기, 이후 이슈) 프로젝트 파일 아래에 다른 값의 층이 있어야 한다.

같은 파일에 사람마다 다른 선택도 들어 있다. 오케스트레이터 · 역할 러너 · 모델이 커밋되는 생성 파일로 내려간다.

- 실행 계획 `script/harness.plan.json` 에 역할마다 벤더 · 실행 인자 · 모델 · 로그인 확인 명령이 실리고, `check` 가 그것을 대조한다(0008)
- 역할 어댑터(`.claude/agents/*.md` · `.codex/agents/*.toml`)에 모델이, 절차 문서의 CLI 러너 단계 제목에 벤더 이름이, `script/harness.env` 에
  리뷰어 표시(`REVIEWER_LABEL`)가 들어간다
- 같은 리포를 쓰는 두 사람이 다른 에이전트 CLI 를 고르면 생성 파일이 달라져 서로의 `check` 를 깨뜨린다

지금 동작 가운데 층을 들이면 성립하지 않는 것이 있다.

- 역할은 `[roles.<역할>]` 표를 지워서 뺀다. 내장 기본값에 일곱 역할이 있고 테이블을 키 단위로 깊게 병합하면, 프로젝트가 표를 지워도 아래 층이
  그 역할을 되살린다
- 구현자와 리뷰어의 러너가 같으면 render 가 거부한다(0003). 개인 선택이 커밋 생성물에서 빠지면 render 는 개인 선택을 보지 않으므로, 개인
  오케스트레이터가 만드는 같은 러너 조합을 볼 수 없다
- 서브에이전트(`inproc`) 역할과 CLI 러너 역할은 절차 문서의 구조가 다르다. 단계 제목 · 본문 · 리뷰 루프가 러너 방식에 따라 갈린다

명세는 `docs/spec/207-layered-config.md`.

검토한 대안.

- 개인 의존 값을 실행 시점에 해석하는 자리 — 렌더가 개인 실행 계획을 홈 아래 클론 키 자리(0016)에 따로 쓰고, 스크립트가 그 파일이 있으면
  읽는다. 0002 의 세 부류에 없는 "개인 생성물" 이 생기고, 개인 파일을 고친 뒤 그 계획이 낡았는지 판정하는 규칙과 `check` 밖에 놓이는 파일이 남는다
- 같은 자리 — 커밋되는 실행 계획에 벤더별 후보를 모두 싣고 스크립트가 개인 파일을 직접 읽어 고른다. 병합 · 검증(불변식 · headless 제약 ·
  모델 판정)이 CLI 와 스크립트 두 곳에 생긴다
- 개인 러너의 범위 — 개인 러너로 `inproc` 와 CLI 러너 사이도 바꾸게 한다. 절차 문서가 러너 방식에 중립이어야 해서 agent 단계 본문이
  "실행 계획을 조회해 서브에이전트면 위임, 아니면 실행기" 같은 조건부 지시가 되고, 러너 검사가 실행 시점으로 옮겨 간다. 리뷰 루프는 CLI
  러너를 전제한다
- 같은 범위 — 커밋 생성물은 프로젝트 이하 값을 그대로 담고 개인 값은 스크립트 실행 시점에만 반영한다. 개인 벤더와 절차 문서 · 어댑터의
  표기가 어긋나고, 서브에이전트 역할의 개인 모델은 적용되지 않는다
- 불변식을 보는 자리 — render 가 개인 레이어를 검사에만 읽고 생성물에는 반영하지 않는다. render 의 성공 여부가 사람마다, 그리고 CI 와
  달라지고, 개인 파일만 고치고 render 하지 않은 경우를 잡지 못한다
- 역할을 빼는 표기 — 역할 집합을 정하는 일반 배열 키를 따로 둔다. 역할 이름을 목록과 표 두 곳에 적고, 조직은 목록을 통째로만 잠글 수 있다
- 같은 표기 — `roles` 를 깊은 병합의 예외로 두어 역할 집합을 개인 레이어를 뺀 가장 위 층이 정하게 한다. 기존 사본과 회귀 테스트는 그대로
  돌지만, 역할 하나를 고치려 해도 역할 표 전부를 적어야 하고 preset 이 역할 하나를 고치면 역할 집합이 그 하나로 줄어든다
- 잠금의 표기 — 층 옆에 별도 정책 파일을 둔다. preset 하나가 파일 둘이 되고, 받기 · lock 이 두 파일을 함께 다뤄야 한다
- 잠금을 선언하는 층 — 프로젝트도 선언하게 한다. 프로젝트가 개인 선택 키를 잠가 사람마다 CLI · 모델을 고르는 목적이 막힌다
- 잠긴 키에 같은 값 — 아래 층이 같은 값을 적어도 거부한다. 지금 모든 프로젝트가 전체 값 사본이라, 잠금을 쓰는 preset 을 받는 순간 기존
  프로젝트가 모두 멈추고, 사본을 줄이는 이관이 먼저 있어야 한다

## Decision

우리는 설정을 고정된 순서의 층으로 해석하고, 위 층이 아래 층을 키마다 하네스가 고정한 병합 규칙으로 덮게 하기로 한다. 층은 아래부터 내장
기본값(`templates/defaults.toml`) ← preset ← 프로젝트 `harness.toml` ← 개인 `harness.local.toml` 이다.

- 병합 규칙은 키마다 하네스의 규칙 표에 고정하고 연산자 문법을 두지 않는다. 스칼라는 덮어쓰고, 테이블은 키 단위로 깊게 병합하고, 일반
  배열은 통째로 바꾼다. 보호 목록(`docs.protected` · `branches.protected`)은 합집합이라 위 층이 아래 항목을 빼지 못하고, `verify.checks` 는
  `name` 으로 짝지어 병합하고, 절차(`workflows.<이름>`)는 절차 하나를 통째로 바꾼다. 같은 키의 형이 층마다 테이블 · 배열과 그 밖으로 갈리면
  병합하지 않고 멈춘다
- 개인 레이어를 뺀 층의 병합이 공유 설정이고, 생성 파일과 `check` 는 공유 설정에서만 나온다. 개인 레이어를 더한 실효 설정은 실행
  (`harness run` · `harness run-plan`)과 점검만 읽는다
- 사람마다 다른 선택은 생성 파일에 넣지 않고 실행할 때 CLI 가 실효 설정에서 해석한다. 역할을 어떻게 띄우는지(실행 계획)는 CLI 가 실행 시점에
  계산해 내고(`harness run-plan`), 그것을 쓰는 스크립트는 고정 사본 CLI 를 불러 받는다. 커밋되는 실행 계획 파일 `script/harness.plan.json` 은
  두지 않는다. 역할 어댑터에 모델을, 절차 문서에 벤더 이름을, `script/harness.env` 에 리뷰어 표시를 쓰지 않는다
- 개인 레이어는 키 넷만 받는다 — `harness.orchestrator` · `harness.model` · `roles.<역할>.runner` · `roles.<역할>.model`. 개인 러너는
  공유 설정의 러너 방식(서브에이전트 또는 CLI 러너)을 유지하고 CLI 만 고른다. 서브에이전트 역할은 오케스트레이터의 모델로 돌므로 그 역할의
  개인 모델은 받지 않는다. 받지 않는 키와 값이면 개인 레이어를 읽는 명령이 거부한다
- 역할은 역할 표 안의 참 · 거짓 키 `roles.<역할>.enabled` 로 끈다. 꺼진 역할은 설정에 없는 역할과 같다
- 잠금은 층 파일 최상위의 키 경로 목록 `locked` 로 적고, `verify.checks` 항목은 항목 안의 `locked = true` 로 적는다. 잠금은 내장 기본값과
  preset 만 선언한다. 스칼라와 일반 배열을 잠글 수 있고, 보호 목록 · `verify.checks` 전체 · 개인 레이어가 받는 키 넷은 잠그지 않는다. 위
  층이 잠긴 키에 잠근 층까지의 병합 값과 같은 값을 적으면 받고, 다르면 거부한다. 배열은 원소와 순서가 모두 같아야 같다

병합과 검증을 CLI 한 곳에 두는 것은 같은 규칙이 스크립트에 두 벌 생기지 않게 하기 위해서다. 개인 러너를 러너 방식 안에 묶는 것은 러너
방식이 절차의 구조이고 그것은 프로젝트가 정하는 것이기 때문이다. 역할을 끄는 키를 스칼라로 두는 것은 새 병합 규칙 없이 덮어쓰기와 잠금만으로
표현되기 때문이고, 같은 값을 받는 잠금은 전체 값 사본을 가진 기존 프로젝트가 이관 없이 잠금을 쓰는 preset 을 받게 하기 위해서다.

## Consequences

- 0001 을 대체한다. 값을 고치는 자리가 프로젝트 값은 `harness.toml`, 기본값은 내장 기본값, 개인 선택은 `harness.local.toml` 로 나뉜다.
  생성 파일을 손으로 고치지 않고 `render` 로 다시 만들며 `check` 와 pre-commit 이 일치를 지키는 것은 그대로이고, 그 입력이 공유 설정이 된다
- 0003 Decision 의 "구현자와 리뷰어의 러너가 같으면 `render` 를 거부" 부분을 이 결정이 대체한다. 불변식은 두 시점에서 본다 — render ·
  check · 프로젝트 레이어 `set` 은 공유 설정으로, 실행(`harness run` · `harness run-plan` · 실행 계획을 받는 스크립트)과 `set --local` 은 실효
  설정으로 보고 거부한다. 역할을 나누는 결정과 `distinct_from` · `invariants.distinct_reviewer` 는 그대로다
- 0008 Decision 의 "둘에서 역할별 실행 계획 `script/harness.plan.json` 을 생성하고, 공용 실행기 `script/run-agent.py` 가 그 계획대로 띄운다"
  부분과 Consequences 의 "실행 계획은 생성물이라 `check` 대상이다" 를 이 결정이 대체한다. 실행 계획은 벤더 선언과 역할 선언에서 CLI 가 실행
  시점에 계산하고, 실행기는 그것을 받아 띄운다. 벤더 선언 등록부와 역할 선언, 모델 목록을 코드에 적지 않는 결정은 그대로다
- 같은 리포의 생성 파일과 `check` 결과가 개인 선택과 상관없이 같다. 대신 개인 선택으로만 생기는 성립하지 않는 조합(같은 러너 등)은 render 가
  아니라 실행할 때 드러난다
- 스크립트가 실행 계획이 필요할 때마다 고정 사본 CLI 를 한 번 띄운다. 스크립트가 CLI 의 하위 명령으로 옮겨 가면 같은 프로세스의 호출이 된다
- 서브에이전트 역할은 역할마다 모델을 고르지 못하고 오케스트레이터 모델 하나로 돈다. 개인 러너로 서브에이전트와 CLI 러너를 바꾸지 못한다.
  허용 값을 넓히는 것은 나중에 받는 값만 늘리면 되지만, 좁히면 이미 쓴 개인 파일이 거부된다
- 역할 표를 지워 역할을 뺀 기존 전체 값 사본은 갱신 뒤 내장 기본값이 그 역할을 다시 켠다. 그 경우를 판정해 render 가 멈추고 끄거나 받아들이는
  명령을 안내한다. 역할이 아닌 테이블 키를 지운 사본은 판정하지 않고 아래 층 값으로 채워진다
- 아래 층의 보호 목록 항목과 `verify.checks` 항목을 위 층이 빼는 표기가 없다
- `roles.<역할>.enabled` · `locked` 는 설정 형식이라 preset 과 프로젝트 파일에 퍼진 뒤에는 이름과 뜻을 바꾸기 어렵다. 잠금 판정은 preset 이
  채워지기 전부터 동작하고, 선언하는 층이 생기는 것은 preset 받기부터다
- 개인 파일이 커밋되면 모든 클론의 선택이 되므로, 하네스는 git 공통 디렉터리의 `info/exclude` 에 줄을 적고 `check` 가 추적되는 개인 파일을 거부한다.
  프로젝트의 `.gitignore` 는 고치지 않는다
- 이 결정에서 바뀐 현재형 사실은 `.ai/project/` 의 scope · glossary · architecture · testing 에 반영한다
