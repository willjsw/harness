# 17. The harness changes the target repo only through safe paths

Date: 2026-10-05

## Status

Proposed

## Context

하네스는 대상 리포의 파일을 만들고 덮고 지우고 옮긴다 — render 의 관리 · 생성 · 소유 파일과 매니페스트, 정리(`prune()`),
`--adopt` 의 넘겨받기, install 의 사본 교체와 설정 씨앗, uninstall, `steps --rename`. 이 지점들은 경로를 저마다 `target / rel` 로
조립해 왔고, 경로 성분이 심볼릭 링크면 링크를 따라 리포 밖의 파일을 바꾼다. `steps --rename` 은 새 이름 자리에 있는 파일을 덮는다.

지울 경로의 출처 하나는 디스크에서 읽는 매니페스트(`.harness/generated` · `.harness/managed`)다. 매니페스트는 대상 리포에 커밋된
파일이라 손편집, 병합 충돌 표지, 소스 리포와의 병합 충돌, 사본 없이 돈 install 이 남긴 줄이 그대로 들어온다. `..` 나 절대 경로가
든 줄은 정리 · 제거가 리포 밖의 파일을 지우게 한다.

#58 의 구현 리뷰(PR #154)는 이 계열의 blocker 를 회차마다 새 지점에서 찾았다. 지점마다 링크 검사(`refuse_link` · `linked_component`)를
덧대는 방식은 규칙의 정의 없이 지점 수만큼 판정이 갈라지고, 덧대지 않은 지점이 남으면 같은 blocker 가 다시 나온다.
위협 모델은 0015 의 Context 와 같다 — 대상 리포에 쓰기 권한이 있는 쪽은 고정 사본을 직접 고칠 수 있다.
명세는 `docs/spec/58-separate-managed-and-project-parts.md` 11절 · 2-3 · 3-2 · 4-1 · 10절.

검토한 대안.

- 규칙의 위치 — 경로 안전을 새 이슈로 분리하고 #154 의 링크 방어를 유지한다. 부분 방어가 규칙의 정의 없이 머지되고, 새 이슈가
  같은 함수를 다시 갈아엎는다. 분리하면서 #154 의 링크 방어를 되돌리면 #154 의 이력과 #147 의 완료 조건을 다시 바꿔야 한다
- 적용 범위 — #58 이 만든 지점만 덮고 uninstall · `steps --rename` 은 다음으로 넘긴다. 예외 지점이 남으면 같은 계열의 blocker 가
  다시 나온다. #154 리뷰 4회차가 그 경우였다
- 링크 — 덮거나 지우는 경로만 거부하고, 소유 파일처럼 없을 때만 까는 경로는 링크인 부모를 허용한다. 엄격하게 시작해 나중에
  완화하는 비용은 작지만, 허용해 두고 나중에 막으면 그 링크에 기대는 기존 설치가 깨진다
- 링크 — `realpath` 가 하네스 루트 안이면 허용한다. "루트 안" 의 경계 정의(루트 자신이 링크인 경우, 루트 안 다른 리포 등)가 더 필요하고,
  해석 시점과 사용 시점 사이의 경합 창이 넓어진다
- 매니페스트 — 쓰는 쪽(render · install)만 형식을 강제하고 읽는 쪽은 믿는다. 사본 없이 돈 install, 소스 리포와의 병합 충돌,
  손편집이 실제로 매니페스트에 줄을 남기므로 쓰는 쪽의 강제로는 읽는 쪽에 도달하는 줄을 막지 못한다
- 매니페스트 줄의 링크 — 매니페스트 검증이 줄의 경로에 있는 링크 성분도 판정하고 그 줄을 매니페스트 안내문으로 보고한다. 같은 링크를
  사전 판정과 매니페스트 검증 두 곳에서 판정하게 되고, 같은 링크라도 그 아래 경로가 매니페스트에 있느냐에 따라 보고 형식이 달라진다
- 매니페스트 줄의 링크 — 매니페스트 검증이 링크를 보는 채로 두고, 링크 아래 경로가 매니페스트에 있는 경우의 기대(링크 하나로 묶은 보고,
  설정을 바꾸는 명령의 되돌리기)를 바꾼다. 같은 이유로 보고 형식이 링크의 위치가 아니라 매니페스트 내용에 따라 갈린다
- 잘못된 줄 — 건너뛰고 경고한다. 그 줄이 가리키던 파일을 정리가 놓친다
- 잘못된 줄 — 리포 밖으로 나가는 줄만 중단하고 나머지는 건너뛴다. 두 부류를 정의하는 비용에 비해 얻는 것이 없고, 위반이 있으면
  쓰기 전에 멈춘다는 명세 3-2 의 원칙과 다르다
- 경합 — 디렉터리 fd 와 `O_NOFOLLOW` 로 성분마다 열어 링크를 끼워 넣을 창을 닫는다. 같은 쓰기 권한이면 사본을 고칠 수 있다는
  위협 모델과 맞지 않고, 구현과 플랫폼별 차이(macOS · Linux 의 `openat` 계열) 비용이 크다. 공용 함수 하나 안의 교체로 나중에 강화할 수 있다
- 기록 — 0015 를 대체한다. 0015 의 결정(막지 않고 감지한다)은 바뀌지 않으므로 `.ai/adr.md` 의 대체 규칙에 맞지 않는다.
  기록을 남기지 않는다 — 대상 리포에서 보이는 동작(멈추는 조건과 출력)이 바뀌고 대안이 셋 이상이라 나중에 "왜" 가 나온다

## Decision

우리는 하네스가 대상 리포를 하네스 루트 아래의 정규 상대 경로로만 바꾸고, 그 경로의 성분에 심볼릭 링크를 거치지 않으며,
디스크에서 읽은 경로(매니페스트)도 같은 규칙으로 검증하고, 위반이 하나라도 있으면 아무것도 바꾸지 않게 한다.

- 경로 규칙은 하나다 — `/` 로 나눈 성분이 `[\w.-]+` 이고, 절대 경로 · 빈 성분 · 끝의 `/` · `.` · `..` 성분이 없으며, 하네스 루트 아래의
  성분 가운데 심볼릭 링크가 없다. 하네스 루트 자신과 그 위는 보지 않는다
- 대상 리포를 바꾸는 지점은 전부 공용 함수 하나(`guarded_path()`)가 돌려준 경로에만 시스템 호출을 한다. 새 지점도 같다
- 변경 명령은 무엇이든 바꾸기 전에 매니페스트 검증과 이번에 바꿀 경로 전부의 사전 판정을 돈다. 어긋나면 종료 코드 2 로 멈춘다
- 매니페스트 검증은 줄의 문자열(형식)만 보고, 링크 성분은 매니페스트 줄이든 아니든 사전 판정과 공용 함수가 판정해 한 형식으로 보고한다
- 읽기 명령(`check` · `doctor`)은 멈추지 않고 어긋난 줄을 보고하며, 그 줄의 경로를 읽지 않는다
- 경합은 사전 판정과 공용 함수 안의 직전 재검사까지 덮는다

정의 없는 지점별 방어가 아니라 규칙 하나를 두는 것은 지점마다 판정이 갈라져 같은 blocker 가 되풀이되기 때문이고,
`O_NOFOLLOW` 계열로 경합 창을 닫지 않는 것은 같은 쓰기 권한이면 사본을 직접 고칠 수 있는 위협 모델에서 얻는 것이 비용보다 작기 때문이다.

## Consequences

- 0015 를 대체하지 않는다. 0015 는 사본 · 관리 파일의 변경을 감지하는 결정이고, 이 결정은 하네스가 대상 리포를 바꾸는 경로의 규칙이다
- 하네스 루트 아래의 심볼릭 링크를 지원하지 않는다. `.ai/project` · `docs/adr` · `script` 같은 디렉터리를 링크로 둔 기존 설치는 이 규칙이 든
  하네스로 갱신하면 render · install · set · steps · checks · uninstall 이 멈추고, 링크를 실제 디렉터리로 바꿀 때까지 대상 리포를 바꾸지 않는다
- 병합 충돌 표지가 남은 매니페스트에서는 변경 명령이 멈춘다. 사람이 표지 줄을 지우고 `harness install` 로 다시 쓰게 해야 한다
- 매니페스트가 신뢰하지 않는 입력이라는 사실을 `.ai/project/architecture.md` "신뢰 경계" 에 적는다
- 재검사와 실제 시스템 호출 사이에 링크를 끼워 넣는 창은 남는다. 직전 재검사가 명령 도중에 멈추면 그때까지 바꾼 파일은 되돌리지 않는다
- 하드 링크는 판정하지 않는다. 하네스가 덮는 파일이 리포 밖 파일과 하드 링크로 묶여 있으면 그 파일도 바뀐다
- `steps --rename` 은 새 이름 자리에 무엇이든 있으면 멈춘다. 하네스가 덮어쓰는 것은 이전 매니페스트에 있는 관리 · 생성 파일과 `--adopt` 뿐이다
- 공용 함수 하나가 경계이므로 경합 창을 닫는 방식(디렉터리 fd 등)으로 바꿀 때 호출 지점은 그대로 둔다
