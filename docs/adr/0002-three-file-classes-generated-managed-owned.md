# 2. Three file classes: generated, managed, owned

Date: 2026-09-23

## Status

Accepted

## Context

하네스를 갱신하면 어떤 파일은 덮어야 하고(역할 계약·배관 스크립트) 어떤 파일은 건드리면 안 된다
(프로젝트가 쓴 사실). 한 파일 안에 두 성격이 섞이면 갱신할 방법이 없다 — 규칙 정본이 프로젝트 사실을
직접 담고 있으면 하네스가 규칙을 고칠 때 사실을 잃거나, 사실을 지키느라 규칙을 못 고친다.

검토한 대안.

- 전부 생성. 프로젝트의 산문을 설정에 넣어야 하고, 설정이 문서가 된다
- 전부 관리(복사). 프로젝트가 고친 것을 다음 갱신이 덮는다
- 갱신 때 병합. 세 방향 병합이 문서에서는 예측되지 않는다

## Decision

우리는 파일을 세 부류로 나누고 부류가 곧 갱신 경계이게 한다. **생성**은 설정에서 나오고 갱신이 다시
만든다. **관리**는 하네스 것이라 갱신이 덮는다. **소유**는 프로젝트 것이라 없을 때만 깔고 갱신이
건드리지 않는다. 규칙 정본은 소유 파일의 본문을 포함해 생성되므로, 사실은 소유 파일에서 고치고 규칙은
설정에서 고친다.

## Consequences

- `.ai/project/` 가 프로젝트 사실의 자리다. 규칙 정본(`.ai/AI_AGENT.md`)의 1~5장은 그 본문이다
- 역할·절차에 이 프로젝트만의 지시를 더하려면 소유 파일(`.ai/project/roles/`·`workflows/`)에 쓰고,
  render 가 생성물 끝에 붙인다. 관리 파일을 고치면 다음 갱신이 덮는다
- 어느 파일이 어느 부류인지를 매니페스트(`.harness/generated`·`managed`)가 갖는다. 제거가 그것으로
  하네스 것과 프로젝트 것을 가른다
- CI 설정은 첫 설치 때만 깔리는 소유 파일이다. 하네스가 만든 것인지 원래 있던 것인지 가릴 수 없어
  지우지 않는다
