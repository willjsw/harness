# 23. Work starts are locked by creating a dedicated ref

Date: 2026-10-10

## Status

Proposed

## Context

같은 리포를 여러 사람 · 여러 클론이 돌리면 두 클론이 같은 이슈의 `work` 를 동시에 착수할 수 있다. 착수 판정은 이슈에 열린
리뷰 요청이 있으면 착수를 거부하지만, 판정과 리뷰 요청 생성 사이에 틈이 있다. 리뷰 요청이 생긴 뒤에도 같은 리뷰 요청의
회차 라벨 갱신과 요약 등록이 클론 사이에서 겹칠 수 있다 — 0004 의 "회차는 한 주체가 센다" 는 한 실행 안에서만 성립한다.
조직 공용화 로드맵은 서버를 두지 않고 forge 를 공유 상태의 정본으로 쓰며, 동시 착수를 forge 기반 잠금으로 막기로 했다.

제약과 사실.

- 구현자는 작업 브랜치 `<태그>/<번호>-<영문-요약>` 의 요약을 스스로 짓고 구현을 끝낸 뒤 push 한다. 두 착수가 같은 브랜치
  이름으로 부딪히지 않는다
- 비강제 push 는 원격 값과 같은 커밋이면 up-to-date 로, fast-forward 면 그대로 성공한다. "같은 이름 ref 의 비강제 push 는
  하나만 성공한다" 는 무조건 성립하지 않는다. 배타가 성립하려면 생성 전용 push(기대값을 비운 lease)여야 한다
- 이슈 담당자는 이슈를 만들 때 필수 필드로 채워진다(`issues.required_fields`). GitHub 는 담당자를 여럿 둘 수 있고, 담당자가
  하나뿐인 트래커에서는 나중에 쓴 쪽이 덮는다. 라벨 추가는 멱등이고 누가 붙였는지 담지 않는다. forge 어댑터 계약에는 조건부
  갱신이 없다(0006)
- pre-push 훅은 HEAD 가 아닌 리비전의 push 를 거부하고 모든 push 에 검증 일괄을 돈다. 명령 가드는 `--force-with-lease` ·
  `--delete` push 를 막는다. 되감기는 원격 브랜치를 지우지 않는다
- GitHub · GitLab 이 `refs/heads/` 밖 이름공간의 생성 · 삭제 push 를 받는지, 받을 때 기대값 검사를 하는지는 실제 forge 로
  확인하지 않았다

검토한 대안.

- 이슈 담당자 · 라벨. 필수 필드 규칙과 담당자의 뜻(담당자 = 착수자)을 바꾸고, 쓰고 다시 읽어 둘 이상이면 물러나는 규칙을
  두어야 배타에 가까워진다 — 둘 다 물러나는 경우도 다뤄야 한다. 트래커 어댑터에 라벨 · 담당자 함수를 세 forge 에 새로 두어
  미검증인 GitLab · Jira 표면이 넓어진다
- 이슈 선점 댓글과 서버 순서. 해제 표지가 없는 가장 이른 선점 댓글이 이긴다. 세 forge 의 어댑터에 작성자 · id · 시각을 담은
  이슈 댓글 조회를 더해야 하고, 정확성이 서버의 쓰기 뒤 읽기 일관성에 달려 있어 로컬 테스트로 고정할 수 없다. 공개
  리포에서는 댓글 권한만 있으면 누구나 착수를 막을 수 있다
- 같은 이름 브랜치의 비강제 push. 위 사실대로 배타가 성립하지 않는다
- 잠금 ref 를 `refs/heads/` 아래에 둔다. 브랜치 목록에 보이고, 조직의 브랜치 이름 규칙에 걸릴 수 있다
- 리뷰 요청을 만들 때 푼다. 착수 틈만 막고 리뷰 회차의 겹침은 남는다. 같은 클론에서 끊긴 실행을 이어 돌리면(#212) 열린
  리뷰 요청 검사가 착수 뒤의 배타를 대신하지 못한다
- 리뷰 명령도 리뷰 요청 단위 잠금을 잡는다. 손으로 부른 실행까지 덮지만 잠금 이름공간이 둘이 되고 절차 밖까지 범위가 넓어진다
- 드라이버에 끝 공통 처리 키를 두어, 드라이버가 스스로 낸 stop 과 `--discard` 에서도 해제를 돌린다. 엔진의 절차 스키마가
  늘어 되돌리는 비용이 크고, 기본 절차에서 드라이버가 스스로 멈추는 경우는 드물며, 같은 클론은 다시 돌려 잠금을 이어 받는다

## Decision

우리는 같은 이슈의 착수를 원격 ref `refs/harness/work-lock/<이슈>` 를 생성 전용 push 로 만드는 것으로 잠그고, 그 ref 를 만든
클론이 git 공통 디렉터리의 소유 기록으로 자기 잠금을 알아보게 한다. 배타는 git 서버의 ref 비교-교체로 성립하고, 판정은
push 의 응답이 아니라 원격 값을 다시 읽어 한다. 기본 `work` 는 착수 판정보다 먼저 잠금을 잡고, 끝 상태로 가는 배선마다
해제 단계를 거친다. 하네스가 원격 ref 를 지우는 것은 해제 하나이고, 원격 값이 이 클론이 만든 값일 때만 지운다.

담당자 · 라벨 · 댓글을 쓰지 않는 것은 어댑터 계약에 조건부 갱신이 없어 배타가 성립하지 않기 때문이다. 이 방식은 어댑터
계약을 늘리지 않고, 트래커가 Jira 여도 같으며, 로컬 bare 리포로 회귀 테스트에 고정할 수 있다.

## Consequences

- pre-push 훅은 잠금 이름공간만 담은 push 에 push 전 검증을 돌지 않는다. 섞인 push 에서는 잠금 줄의 리비전만 HEAD 일치 검사에서
  뺀다
- 되감기의 "원격 브랜치를 지우지 않는다" 는 그대로다 — 잠금 ref 는 브랜치가 아니다. 되감기는 이 클론의 잠금을 다른 대상을 모두
  되감은 뒤에 푼다. 명령 가드는 에이전트가 직접 치는 `--force-with-lease` · `--delete` push 를 잠금 ref 에도 막는다. 다른 클론의
  잠금은 사람이 지운다
- 잠금의 소유 단위는 클론이다. 같은 클론의 worktree 는 같은 잠금을 쓴다. 같은 클론 안의 동시 실행은 이 잠금이 막지 않는다
- 잠금은 시간이 지나도 풀리지 않는다. 해제 단계를 거치지 않은 끝 — 드라이버가 스스로 낸 stop, 끊긴 실행, `--discard` 로 버린
  실행 — 은 잠금을 남긴다. 하네스는 자동으로 풀지 않고, 같은 클론은 다시 돌려 이어 가거나 해제 명령으로 푼다
- `work` 경로의 리뷰 회차가 클론 사이에서 직렬화된다. 0004 의 "회차는 한 주체가 센다" 와 0022 의 연속 회차 재구성이 한 번에
  한 등록자를 전제할 수 있다. 손으로 부른 리뷰 명령은 잠금을 잡지 않는다
- 잠금은 협조 규약이다. push 권한이 있으면 누구나 잠금 ref 를 만들고 지울 수 있다. 이 기능을 가진 버전으로 도는 클론끼리만
  배타가 성립한다 — 전환 기간의 옛 클론은 잠금을 모른다
- forge 가 `refs/heads/` 밖 이름공간을 받아야 성립한다. forge 자체 검사의 쓰기 단계가 이것을 확인하고, 받지 않는 forge 에서는
  `work` 가 시작 잠금을 잡지 못하고 멈춘다
- `origin` 의 fetch 주소와 push 주소가 다른 서버를 가리키면 다시 읽기가 push 한 곳을 보지 못해 잠금이 성립하지 않는다
